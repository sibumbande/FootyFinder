# Admin Back Office Implementation

## Architecture decision

The Admin back office is a separately deployable application inside this npm-workspaces monorepo. `apps/admin` uses the shared contracts and API client, while privileged orchestration remains under `/admin` in the existing API and PostgreSQL database. Match, wallet, notification, Team, and booking invariants stay in their existing domain services.

A separate repository, API, or database is intentionally deferred until an independent operating team, regulatory boundary, or deployment lifecycle requires it.

## Compatibility boundaries

- Existing Prisma `Venue` rows remain immutable Match location snapshots.
- The managed catalogue uses separate Venue/Field models and copies a snapshot when a Match books a Field.
- Existing Quick Game entry fees, joining, cancellation, replacement credits, formations, chat, and lifecycle remain supported.
- Private Team Matches remain free HOME-only `DRAFT` planning workspaces and do not reserve Fields or mutate wallets.
- Admin-created playable Matches use `QUICK_GAME` with an explicit Admin source.
- Support tickets never expose unrelated direct messages.
- Suspensions and bans preserve historical and financial records.
- Admin financial actions use typed wallet operations; raw balances and ledger rows are never editable.
- Every privileged mutation and its redacted audit event commit atomically; realtime publication follows commit and is best effort.

## Slice 1 security boundary

- JWTs are bound to persisted, independently revocable `AuthSession` rows. Logout revokes only the current session; account status is checked on every HTTP and Socket.IO authorization.
- Cookie-authenticated mutations require an approved player/Admin Origin. Bearer clients retain their explicit authentication boundary.
- Authentication, chat, conversation, Match/Team/invite creation, uploads, deposits, and other costly mutations use tiered stable `RATE_LIMITED` responses. The included store is intentionally single-process; production horizontal scaling requires a shared implementation.
- Socket sessions are indexed by user and session. Participation/membership revocation evicts active sockets, reconnects rejoin authorized rooms and refetch authoritative state, and socket failures expose stable public errors.
- Private Quick Match invitations are stored only as SHA-256 digests. Plaintext tokens are returned once at creation/rotation and can be regenerated by the host.
- Helmet, trusted-proxy validation, explicit production HTTPS checks, request IDs, redacted structured logs, multi-origin CORS, and cross-platform upload containment establish the deployment baseline used by the Admin application.
- `smoke:security-sessions` exercises persisted cookie auth, origin enforcement, independent logout, account restriction, hashed invite rotation, Socket.IO room eviction/revocation, safe reconnect rejection, and exact PostgreSQL cleanup.
